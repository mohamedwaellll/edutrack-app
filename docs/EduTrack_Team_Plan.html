الحسابات والصلاحيات والعقد المشترك

feature/auth-role-access

المطلوب تنفيذه

  1. يثبت عقد الربط وأسماء الحقول والخدمات مع محمد قبل توصيل البوابات.
  2. يربط حساب المدرس بسجل المدرس والطالب بسجل الطالب، وينشئ علاقة صريحة بين ولي الأمر وأبنائه.
  3. يجهز الدخول والتوجيه للأدوار الأربعة، مع حالات البروفايل أو الربط المفقود.
  4. يفرض الصلاحيات في قاعدة البيانات: المدرس لمجموعاته، الطالب لنفسه، وولي الأمر لأبنائه.
  5. يراجع شغله القديم على فرع ali وينقل الأجزاء المناسبة إلى React/Vite؛ لا يدمج Next.js كاملًا.

نقبل التسليم لما...

  • اختبار حسابين من كل دور ومحاولات الوصول لبيانات غير مرتبطة.
  • منع تعديل الدور وروابط الحسابات من العميل.
  • عدم وصول الملاحظات الداخلية لولي الأمر حتى بطلب API مباشر.
  • طريقة إدارية موثقة وآمنة لإنشاء وربط حسابات العرض.

طريقة التجميع

تنفيذ متوازٍ ودمج منظم

  1. محمد يغلق تصحيحات إدارة المدرسين، وعلي يعتمد العقد معه بالتوازي.
  2. عبدالرحمن يثبت QR؛ مينا ويوسف يبدآن واجهاتهما واختباراتهما وفق العقد.
  3. نُدمج تصحيحات محمد، ثم أساس الحسابات والصلاحيات من علي.
  4. كل عضو يحدّث فرعه من develop ويكمل الربط الحي.
  5. محمد يدمج PR واحدًا في كل مرة، ويختبره قبل الانتقال للي بعده.

تشغيل نسخة جديدة

git clone https://github.com/mohamedwaellll/edutrack-app.git
cd edutrack-app
git fetch origin --tags
git switch --track origin/feature/student-portal
npm ci

اختار فرعك بدل فرع الطالب، بعد تأكيد نشره. استخدم Node 26.8.1. انسخ .env.example إلى .env فقط لو الملف غير موجود، وخد إعدادات التطوير من المسؤول.

قبل التسليم

git fetch origin
git merge origin/develop
npm test
npm run build

احفظ شغلك في commit قبل الدمج. راجع التعارضات مع مالك الملف. افتح PR إلى develop، من غير force push أو reset --hard.

الملفات المشتركة: App وAuth والأنواع العامة عند علي؛ الحزم وCI عند محمد. لا تتكرر أسماء migrations، ولا تُعدّل ملفات SQL التاريخية.

دعوات المتعاونين وحماية الفروع إعدادات منفصلة يحتاج محمد يتأكد منها؛ إنشاء الفروع وحده لا يفعّلها.

اعتماد التسليم والعرض

نعرف إن المشروع جاهز إزاي؟

الدورالصلاحيات المتفق عليها
الأدمنالإدارة والربط وتسجيل الحضور وفق المسارات المعتمدة.
المدرسمجموعاته وطلابها وإضافة درجات وملاحظات مسموحة.
الطالببياناته ومجموعته وحضوره ودرجاته وكارته فقط.
ولي الأمرأبناؤه المرتبطون بالحساب وملاحظاتهم المسموحة فقط.

سيناريو عرض واحد يجمع الأجزاء

  1. الأدمن ينشئ مدرسًا ومجموعة وطالبًا ويربط حسابات التجربة.
  2. مسح الكارت يسجل الحضور، والتكرار يحافظ على وقت الوصول.
  3. المدرس يضيف درجة وملاحظة لطالب في مجموعته.
  4. الطالب يرى الدرجة والحضور بعد إعادة التحميل.
  5. ولي الأمر يرى ابنه والملاحظة المسموحة؛ الداخلية لا تصله.
  6. حسابات أخرى لا تستطيع الوصول بتغيير المعرفات.

تقرير كل تسليم

الملفات المعدلة، migrations وترتيبها، أوامر ونتائج الاختبارات والبناء، حالات الفشل، التجربة اليدوية والقيود الباقية.

اكتب PASS أو FAIL أو BLOCKED مع البيئة. الاختبار المحلي لا يساوي تجربة Supabase حي أو كاميرا فعلية.

بوابة الاعتماد: اختبارات ناجحة + بناء ناجح + تحقق صلاحيات + تجربة متصفح فعلية. بعدها نجهز إصدار العرض المستقر على main.

قبل العرض: بيانات صناعية، تجربة الموبايل، فيديو احتياطي، وشرح الميزات غير المكتملة بوضوح. المقياس هو مرور نفس البيانات بين الأدوار، مش مجرد وجود شاشات.

راجع ACCEPTANCE_CHECKLIST.md وHANDOFF_STATUS.md. عقد INTEGRATION_CONTRACT.md مقترح يحتاج اعتماد علي ومحمد قبل الربط الحي.
